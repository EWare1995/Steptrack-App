## Application code prepared

- `components/Main.js` is feature-gated with `NEXT_PUBLIC_STO_STORAGE_ENABLED=true`. **Do not set the flag in production or preview yet.** Its default is false.
- When enabled after schema validation, each trial STO's editor stores `qualifying_days` and enforces written/structured ratio and day parity.
- `components/StoTrialEntryPanel.js` gives a per-STO live X/O or manual logger, multi-select supports, chosen date, location, notes, and independent qualifying-day history.
- `lib/stoTrialProgress.js` independently aggregates by `sto_id` + calendar date and never credits another STO. The app reads `sto_trial_entries` separately from the existing annual-goal `logs` table to prevent double counting.
- The frontend never substitutes for RLS or backend input validation.

## Database contract to validate against actual schema

**Do not copy or execute any SQL from this document.** After separately authorized read-only schema confirmation, generate a real migration with the Supabase CLI in a disposable development project.

1. Add a nullable positive-integer `qualifying_days` field to `sto_objectives`. Null means not yet configured for legacy STOs; never infer success or impose new defaults on old records.
2. Introduce `sto_trial_entries` with the following fields and server-side constraints:
   - `id`: UUID primary key, generated by DB.
   - `sto_id`: non-null UUID foreign key to `sto_objectives(id)`.
   - `goal_id`: non-null UUID foreign key to `goals(id)`.
   - `child_id`: non-null UUID foreign key to `children(id)`.
   - `logged_by`: non-null authenticated user UUID, server-validated as `auth.uid()`.
   - `logged_on`: non-null date, never future-dated unless separately approved.
   - `value`: non-null nonnegative integer successes.
   - `trial_total`: non-null positive integer opportunities, with `value <= trial_total`.
   - `supports`: validated text array of allowed support labels, preferably nonempty.
   - `setting`: text; `note`: text, with input length limits.
   - `created_at`: immutable server timestamp.
3. Database must verify `sto_id -> goal_id -> child_id` consistency on **every** insert; client-provided IDs are not trusted. Enforce this in a checkable RLS predicate and, ideally, immutable composite foreign keys/constraint triggers.
4. Enable RLS, revoke public/anon table access, explicitly grant only needed privileges to authenticated users. `SELECT` requires verified active membership in the specific child's team. `INSERT` requires verified active membership, `logged_by = auth.uid()`, and valid child/goal/STO chain. Do not rely on client `can_edit_goals`; aides can create trial logs without editing STOs.
5. No `UPDATE` policy for STO entries until edit semantics are designed. `DELETE` policy, if supported, must mirror existing role rules: parent may remove authorized child entries; aide may not remove older-day entries. Audit deletes and consider soft-delete where existing governance requires it.
6. Ensure an STO may not be moved to a different parent goal after entries exist without protected migration and audit. STO field editing rights continue to use existing `sto_objectives` RLS.
7. Index `(sto_id, logged_on)` and `(child_id, logged_on)` for child-isolated reads. Review retention, backups, audit events, and report implications.
8. Keep all legacy parent-goal `logs` entries unchanged; STO entries must **not** be copied into annual-goal progress without an explicit future product decision.
